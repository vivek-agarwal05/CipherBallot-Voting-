CipherBallot Cryptographic & Privacy Model

An honest appraisal of the cryptographic primitives, architectural safeguards, assumptions, and privacy trade-offs implemented in this college educational prototype.

Educational Prototype — Not Suitable For Production or Binding Elections

CipherBallot demonstrates fundamental cryptographic principles (authenticated symmetric encryption, digital signatures, password hashing, and hash-chain audit logs). It does not implement an end-to-end verifiable cryptographic voting system (such as Helios, ElectionGuard, or Neff mixnets) and does not guarantee coercion resistance or protection against a compromised server administrator.

Cryptographic Primitives Employed

Security Function Algorithm / Standard Parameters Why Chosen
User Password Hashing Argon2id Memory=64MB, Iterations=2, Parallelism=2 Resistant to GPU/ASIC cracking and side-channel cache attacks (RFC 9106).
Hybrid Key Encapsulation RSA-2048 OAEP (SHA-256) Unique AES-256 key per ballot wrapped with RSA public key Combines asymmetric key distribution (Unit III) with fast symmetric AEAD encryption (Unit II).
Ballot Confidentiality & Integrity AES-256-GCM Ephemeral 256-bit key, 96-bit random nonce, 128-bit tag Authenticated encryption provides confidentiality and detects ciphertext modification.
Transport Security HTTPS / TLS (X.509) Local self-signed X.509 cert (RSA-2048 + SHA-256) Protects voter credentials, session cookies, and ballots in transit from network sniffing.
Ballot Binding (AAD) AES-GCM AAD Canonical JSON of (election_id, ballot_id) Prevents ciphertext transplantation across elections or ballot slots.
Verifiable Receipt Digest SHA-256 256-bit cryptographic digest One-way hash over ciphertext parameters allowing bulletin board lookup without decryption.
Published Result Signature Ed25519 RFC 8032 Curve25519 (Edwards curve) Fast, deterministic, collision-resistant signatures to authenticate certified election outcomes.
Tamper-Evident Audit Chain SHA-256 Chain prev_hash || canonical_payload Detects insertion, deletion, or reordering of audit events without central PKI.

Architectural Separation of Identity & Ballots

In traditional naive voting software, a single row often stores (user_id, candidate_id), completely destroying voter secrecy. CipherBallot strictly isolates database tables to eliminate direct identity linkage:

Table: participations

  • Stores (election_id, voter_id, cast_at)
  • Enforces unique constraint preventing duplicate voting
  • NEVER contains candidate choice
  • NEVER contains ballot ID or foreign key

Table: encrypted_ballots

  • Stores (random_ballot_uuid, nonce, ciphertext, tag)
  • Candidate choice is sealed under AES-256-GCM
  • NEVER contains voter ID column
  • No relationship or foreign key to participations

Residual Privacy Trade-offs & Risks

  • Timestamp Correlation Risk: In Variant B, an attacker correlating server access logs or database insertion timestamps could link participations with encrypted_ballots. Mitigation: Variant C introduces two-phase unlinked anonymous voting tokens.
  • Privileged Insider Threat: An administrator holding the RSA private key can decrypt individual ballots after election close. Production systems require threshold cryptography or homomorphic tallying.
  • Coercion & Vote Selling: Verifiable receipts prove inclusion without revealing candidate choices, though formal coercion resistance requires receipt-falsification mechanisms.
